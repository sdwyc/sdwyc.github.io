## 23:00 — 定位崩溃根因：Ruby 4.0 移除 ostruct

- **文件**：`Dockerfile`
- **触发问题**：容器 `Exited (137)`，日志末尾
  ```
  /usr/local/lib/ruby/4.0.0/bundled_gems.rb:60:in 'Kernel.require': cannot load such file -- ostruct (LoadError)
      from /usr/local/bundle/gems/jekyll-twitter-plugin-2.1.0/lib/jekyll-twitter-plugin.rb:6
  ```
  镜像内 `ruby -v` = `ruby 4.0.7`，`Config.Env` 里 `RUBY_VERSION=4.0.7`。
- **原因分析**：`FROM ruby:latest` 已滚动到 Ruby 4.0，`ostruct` 从标准库移除；`Gemfile` 声明了
  `jekyll-twitter-plugin`，该插件 `require 'ostruct'` 直接失败。属上游镜像漂移，不是本仓库代码问题。
- **改动做法**：`FROM ruby:latest` → `FROM ruby:3.3-bookworm`（3.3 与 jekyll 4.4.1、jemoji、
  jekyll-scholar 等插件兼容性最好，且 ostruct 仍是标准库）。
- **验证方式**：镜像内 `ruby -v` = `ruby 3.3.14 (aarch64-linux)`；`bundle exec jekyll` 不再报 ostruct。
- **影响面 / 回滚**：降版本后不再跟随上游新 Ruby；回滚只需改回 `ruby:latest`（会重新崩溃）。

## 23:10 — Gemfile.lock 被 Bundler 4 改写，导致构建反复重装

- **文件**：`Gemfile.lock`（`.gitignore` 忽略，未跟踪）
- **触发问题**：lock 里出现 `BUNDLED WITH 4.0.22` 和 Bundler 4 独有的 `CHECKSUMS` 段；
  用 Ruby 3.3（自带 Bundler 2.5.22）执行时输出
  ```
  Bundler 2.5.22 is running, but your lockfile was generated with 4.0.22.
  Installing Bundler 4.0.22 and restarting using that version.
  ```
  随后卡在 `Fetching source index from https://rubygems.org/` 达 1 小时以上。
- **原因分析**：
  1. 原 `bin/entry_point.sh` 启动时 `rm -f Gemfile.lock`，每次运行都用容器内 Bundler 重新解析并回写 lock，
     于是宿主 lock 被升级成 Bundler 4 格式（时间戳 22:40 即那次崩溃运行写下）。
  2. Bundler 4 会用完整 source index，在国内网络下几乎不可用。
- **改动做法**：
  - 删除 `CHECKSUMS` 段（Bundler 2.5 不识别该段）；
  - `BUNDLED WITH` 改回 `2.5.22`（与镜像自带 Bundler 一致）；
  - 所有 gem 版本号保持不变，仅改格式。
- **验证方式**：构建日志不再出现 "Installing Bundler 4.0.22"，`Bundle complete! 97 gems now installed` 约 30s 完成。
- **影响面 / 回滚**：lock 未纳入版本控制，仅本地生效；备份在 `/tmp/Gemfile.lock.ruby40.bak`。

## 23:20 — 删除 apt 层（debian 源 502 不可用）

- **文件**：`Dockerfile`
- **触发问题**：构建卡在 apt 阶段：
  ```
  #7 1047.9 Err:2 http://deb.debian.org/debian bookworm-updates InRelease
  #7 1047.9   502  Bad Gateway [IP: 146.75.114.132 80]
  ```
  容器内单独跑 `apt-get update && apt-get install jupyter-nbconvert` 挂起 75 分钟无输出。
- **原因分析**：宿主侧网络对 debian 源频繁 502 / 超时；而 `ruby:3.3-bookworm` 基础镜像
  本身已带 `imagemagick 8:6.9.11`、`python3`、`gcc/make/pkg-config`、`zlib.h`，
  构建期实际不需要额外 apt 包。
- **改动做法**：整段 `RUN apt-get update && apt-get install ...` 以及 `locale-gen` 删除，
  改用 `LANG=C.UTF-8 / LC_ALL=C.UTF-8`（Debian 内置 locale，无需生成）。
- **验证方式**：容器内 `convert -version` 正常；最终 `_site/assets/img` 生成 96 个 webp，响应式图片流水线可用。
- **影响面 / 回滚**：`inotify-tools`、`jupyter-nbconvert` 不再安装（见下两条），
  若日后需要 notebook 渲染，需另找可用的 apt 源或 pip 安装。

## 23:25 — 重写入口脚本：不再删除 Gemfile.lock

- **文件**：`bin/entry_point.sh`
- **触发问题**：脚本启动即执行 `rm -f Gemfile.lock`，并带 `inotifywait` 重启循环；
  lock 被反复重写，且在 macOS bind mount 上 inotify 事件不可靠。
- **原因分析**：这是上游为"改了 Gemfile 自动重装"设计的粗暴方案，副作用是把宿主的 lock 删掉，
  造成版本漂移 + 每次启动都要联网解析。
- **改动做法**：
  ```bash
  set -e
  cd /srv/jekyll
  bundle check >/dev/null 2>&1 || bundle install --jobs 4 --retry 3
  exec bundle exec jekyll serve --source /srv/jekyll --destination /srv/jekyll/_site \
    --host 0.0.0.0 --port 8080 --livereload --force_polling --watch --trace
  ```
  - 用 `bundle check` 判断，只在真的不一致时才安装；
  - 用 `bundle exec` 保证使用镜像内 gem；
  - 去掉 inotifywait 循环（改 `_config.yml` 时手动 `docker compose restart`）。
- **验证方式**：冷启动日志 `==> Ruby: ruby 3.3.14 ... / ==> 启动 Jekyll`，
  `bundle check` 通过，无任何联网安装；`done in 79.8 seconds`，`Server running`。
- **影响面 / 回滚**：修改 `_config.yml` 后不会自动重启，需要手动 restart。

## 07:00 — BuildKit 沙箱网络拉 gem 元数据卡死

- **文件**：`docker-compose.yml`、`Dockerfile`
- **触发问题**：`docker compose build` 停在
  ```
  #10 1882.3 Fetching gem metadata from https://rubygems.org/.
  ```
  持续 1.5 小时无进展；期间还报过 `SSL_connect ... certificate verify failed`。
- **原因分析**：BuildKit 构建步骤使用独立沙箱网络，对 rubygems compact index 的
  Range 请求/证书链处理与普通 `docker run` 容器不同（同机 `docker run` 容器内
  `curl https://rubygems.org` 返回 200，单 gem 下载约 50KB/s 正常）。
- **改动做法**：
  - compose 的 build 段加 `network: host`；
  - Dockerfile 的安装层加 `--mount=type=cache,target=/usr/local/bundle/cache` 复用 gem 缓存，
    并 `bundle config set --global retry 5 / timeout 60`。
- **验证方式**：改为 host 网络后 `bundle install` 29 秒装完 99 个 gem，
  日志 `Bundle complete! 23 Gemfile dependencies, 99 gems now installed.`
- **影响面 / 回滚**：`network: host` 仅影响构建期，不进运行时；
  在 Docker Desktop(macOS) 上等价于使用虚机宿主网络。

## 07:15 — mini_racer 预编译二进制与 glibc 不兼容

- **文件**：`Gemfile`、`Dockerfile`
- **触发问题**：
  ```
  /usr/local/bundle/extensions/aarch64-linux/3.3.0/mini_racer-0.22.2/mini_racer_extension.so:
  undefined symbol: __isoc23_strtoll (LoadError)
  ```
- **原因分析**：`mini_racer 0.22.2` 预编译的 `aarch64-linux` 二进制用了 glibc ≥ 2.38 的
  C23 `strtoll` 符号，而 Debian bookworm 是 glibc 2.36。它只是 `execjs` 的 JS 运行时
  （链路：`jekyll-minifier` → `terser` → `execjs`），并非功能必需。
- **改动做法**：
  - `Gemfile` 注释掉 `gem 'mini_racer'` 并写明原因；
  - `Dockerfile` 增加 `FROM node:22-bookworm-slim AS node` 阶段，
    `COPY --from=node /usr/local/bin/node /usr/local/bin/node`（约 100MB 镜像只需几十 KB 产物），
    并设 `EXECJS_RUNTIME=Node`。
- **验证方式**：容器启动无 LoadError；`Jekyll Minifier: Filtering out legacy 'harmony' option`
  正常输出，JS/CSS 压缩环节通过，构建 80s 完成。
- **影响面 / 回滚**：裸机（不走 Docker）开发需要本机装 Node；
  若想恢复 mini_racer，需要 glibc ≥ 2.38 的基础镜像（如 trixie）。

## 07:30 — notebook 转换中断构建

- **文件**：`_config.yml`
- **触发问题**：
  ```
  Conversion error: JekyllJupyterNotebook::Converter encountered an error while converting
  'assets/jupyter/blog.ipynb':
  ```
- **原因分析**：`plugins` 里启用了 `jekyll-jupyter-notebook`，Jekyll 会扫描整个
  `assets/`，遇到演示用 `blog.ipynb` 就要调用 `jupyter nbconvert`；apt 不可用故未安装。

- **改动做法**：`_config.yml` 的 `exclude` 增加 `- assets/jupyter/`。
- **验证方式**：重启后构建无 Conversion error，`/` `/blog/` 等页面 200。
- **影响面 / 回滚**：以后若要发 notebook 文章，需装 nbconvert 并移除该 exclude。

## 07:35 — Gemfile.lock 未纳入版本控制，全新克隆会构建失败

- **文件**：`Dockerfile`
- **触发问题**：`.gitignore` 第 9 行 `Gemfile.lock`，`git ls-files` 无该文件；
  而 Dockerfile 里 `COPY Gemfile Gemfile.lock ./` 在全新克隆时找不到文件。
- **原因分析**：al-folio 上游策略是忽略 lock，由 CI 现场解析。
- **改动做法**：改为 `COPY Gemfile* ./`（有 lock 就一起拷，没有也能构建）。
- **验证方式**：重建成功 `build exit=0`，启动后站点 200。
- **影响面 / 回滚**：无 lock 时会重新解析最新版本，可能引入不兼容（如再次拉到不兼容的 gem）。

## 环境坑位备忘

- 沙箱会拦截 docker 对 `~/.docker` 的写入 → 构建类命令需 `dangerouslyDisableSandbox`；
  或 `BUILDX_CONFIG=/tmp/buildx` 规避 buildx 状态目录权限问题。
- Docker Hub `auth.docker.io` 偶发 502（`failed to fetch oauth token`），
  可先用 `docker pull <image>` 单独拉取，再 `docker compose build`（走本地镜像）。
